# 계약 정보 입력 명세 v0.1

## 목적

계약서 OCR, 사용자 확인, 계약서 검토, 내용증명 생성 사이에서 공유하는
계약 정보의 경계를 정의한다. 적용 범위는 주거용 전세·월세·매매이다.

## 처리 경계

```text
계약서 업로드
  -> OCR 추출 결과
  -> 개인정보 마스킹과 필드 정규화
  -> 사용자 원문 대조·수정·확인
  -> ConfirmedContractSnapshot v0.1
  -> 기능별 LangGraph 입력
```

`ConfirmedContractSnapshot`은 OCR 엔진의 원시 응답이 아니다. 사용자가
확인한 revision을 변경 불가능한 입력으로 고정한 기능 공통 계약 데이터다.

원본 파일과 스냅샷은 저장 시 암호화한다. 암호화된 문자열 자체를 LLM에
전달하지 않는다. 권한 확인 후 필요한 값을 복호화하고, 주민등록번호,
전화번호, 계좌번호 등 기능에 불필요한 개인정보를 제거한 분석용 데이터만
LangGraph와 LLM에 전달한다.

## 공통 계약 스냅샷

공통 부분은 다음 정보를 가진다.

- 계약 체결일
- 목적물 주소, 상세 주소, 주거 유형, 토지·건물·임대 면적과 대지권 정보
- 매도인·매수인 또는 임대인·임차인과 대리인
- 개업공인중개사 사무소·등록번호·담당 공인중개사
- 계약서의 전체 조항과 원문 순서
- 특약 원문과 원문 위치
- 체납·선순위 보증금·등기 확인 등 고지사항
- 당사자 서명·날인 존재 여부
- 첨부·별지 이름
- OCR 원문 위치와 사용자 확인·수정 상태

주민등록번호 필드는 만들지 않는다. 전화번호와 계좌번호는 공통 계약
스냅샷에 보존하지 않는다. 내용증명 문서에 필요한 발신인·수신인 주소는
내용증명 요청에서 사용자가 최종 확인한다.

## 계약 유형별 값

### 전세

- 임대차 보증금과 한글 금액 원문
- 계약금, 중도금·분할 지급, 잔금과 지급일
- 계약 시작일·종료일, 인도일
- 관리비 총액·비목·산정 방식

### 월세

전세 필드에 다음을 추가한다.

- 월 차임
- 매월 지급일
- 선불·후불 여부
- 마스킹된 입금 계좌 표기(화면 확인용이며 LLM 입력에서는 제외)

### 매매

- 매매대금과 한글 금액 원문
- 계약금, 회차별 중도금, 잔금과 지급일
- 목적물 인도일과 소유권이전 예정일
- 근저당·압류 등 권리부담 처리 조건
- 융자금·승계 채무 조건
- 기존 임차인·점유 관계와 승계·공제·명도 조건

## 프론트 OCR 확인 화면

프론트는 계약 유형에 맞는 필드를 그룹별로 표시한다.

1. 문서·계약 유형
2. 목적물
3. 당사자
4. 금액·지급 일정
5. 기간·인도·소유권이전
6. 권리·고지사항
7. 전체 조항
8. 특약
9. 서명·날인과 첨부

각 필드는 OCR 인식값, 사용자가 수정할 최종값, 원문 페이지와 강조 위치,
OCR 신뢰도를 가진다. 신뢰도는 법률 위험도가 아니다. 사용자는 빈칸도
`confirmed_blank`로 확인할 수 있다.

확인 완료 시 서버는 revision을 검사하고 `snapshot_id`를 반환한다. 이후
기능은 화면의 임시 값이 아니라 이 `snapshot_id`를 참조한다.

## 계약서 검토 입력

계약서 검토에는 자유 텍스트 입력을 받지 않는다.

```json
{
  "contract_snapshot_id": "UUID",
  "registry_snapshot_id": "UUID 또는 null"
}
```

서버는 계약 스냅샷과 선택한 등본 스냅샷을 불러와 주소·소유자·권리부담을
규칙 기반으로 먼저 교차검증한다. 그 결과와 개인정보를 제거한 계약 내용을
계약서 검토 LangGraph에 전달한다.

## 내용증명 생성 입력

내용증명은 자연어 하나에 목적과 사실관계를 섞지 않고 `purpose`와 `facts`로
분리한다. 둘 다 사용자가 입력하고 확인하는 필수값이다.

```json
{
  "contract_snapshot_id": "UUID",
  "purpose": "임대차계약 해지 및 보증금 반환 요구",
  "facts": "계약이 종료됐는데 보증금을 돌려받지 못했습니다. ...",
  "sender": {
    "name": "발신인 이름",
    "address": "발신인 주소",
    "detail_address": "상세 주소 또는 null"
  },
  "receiver": {
    "name": "수신인 이름",
    "address": "수신인 주소",
    "detail_address": "상세 주소 또는 null"
  },
  "requested_deadline": "2026-11-15 또는 null",
  "attachment_names": []
}
```

계약서 검토에는 자연어 요청 필드를 제공하지 않는다. 특약 생성과 판례
검색에서는 `user_query`를 계속 사용하지만, 내용증명은 문서 목적과 사실관계
검증이 필요하므로 `purpose`와 `facts`를 사용한다.

## LLM 전달 제외 항목

- 주민등록번호
- 전화번호
- 계좌번호
- 파일 URL과 저장소 키
- 사용자 ID와 DB 기본키
- OCR bounding box와 엔진 신뢰도
- OCR 수정 이력
- 모델명, 처리 시간, 디버그 옵션
- 서명·도장 이미지

실명과 상세 주소는 최종 내용증명 렌더링에는 필요하지만 검색 질의와 법률
분석 프롬프트에서는 당사자 역할과 비식별 값으로 대체한다.

## 로컬 MySQL 스냅샷 저장

개발 서버는 기본적으로 메모리 저장소를 사용한다. 로컬 MySQL을 사용할 때만
`.env`에 `SNAPSHOT_STORE_BACKEND=mysql`과 `MYSQL_HOST`, `MYSQL_PORT`,
`MYSQL_DATABASE`, `MYSQL_USER`, `MYSQL_PASSWORD`를 설정한다. 비밀번호는
`.env.example`, 코드, 테스트, 로그에 넣지 않는다.

MySQL 저장소는 계약서와 등본 스냅샷의 전체 JSON 및 조회용 메타데이터를
별도 테이블에 저장한다. 이는 로컬 개발 단계의 영속화 방식이며, 인증·인가가
도입되기 전에는 외부 공개 환경에 배포하지 않는다. 사용자 소유권 식별자와
암호화 정책은 인증 설계와 함께 확정한다.
